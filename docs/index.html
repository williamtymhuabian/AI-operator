INSIGHTS

三个反直觉的实测现象

如果这些和你想的不一样，这门课就是为你准备的。

现象 01

一行计算都不改，快 21 倍

v0 → v1 只调换了循环顺序，把"沿 B 的列跨步走"变成三条顺序访存流。 收益来自 cache 行利用率和硬件预取，不是算法变聪明了。

0.4 → 7.6 GF/s
现象 02

教科书大招"分块"没变快

v2 的 cache 分块在本机实测 ≈ 0 提升：因为 v1 卡在标量计算瓶颈（8 GF/s）， 访存优化打不中目标。优化必须先定位瓶颈，否则白做。

8.0 → 8.0 GF/s
现象 03

SIMD 内核越快，越容易被饿死

v3 的微内核在 256³ 冲到 67 GF/s，在 2048³ 跌到 10——内存供不上快内核。 v4 用"打包 + 面板"（分块思想的兑现）把它救回来 3.3 倍。

67 → 10 → 33.6 GF/s
MICRO-KERNEL

看懂 4×8 微内核：整个课程的原子操作

BLAS、CUDA、昇腾 Cube 单元的内核形态全部源于此： 一次计算 C 的 4 行 × 8 列，32 个累加数全程驻留寄存器， B 的每个元素读一次、被 4 行 A 复用。按 ▶ 观察一个 k 步发生了什么。

A 面板 4×1
broadcast →
c[r] =
fma(a[r], b,
    c[r])
B 行 1×8（__m256 一次读取）
C 累加器 4×8（寄存器里）
c[0]…c[3] : __m256 k = 0 / 8

每个 k 步：读取 B 的一行（8 个数，一条 load）， 与 4 个 A 标量各做一次 8 路乘加（4 条 FMA）。 8 个 k 步结束才写回内存一次。

一个 B 元素参与 4 次运算 —— 访存复用 ×4； 32 个累加数不落内存 —— C 写回摊薄 8 倍。

瓶颈驱动的优化循环

算子优化不是"想更聪明的算法"，而是这个循环转六圈。 左列是症状，右列是对应的处方——本课程每一级就是一次对症下药。

1

实测

计时 + GFLOP/s，别猜。make run 一切用数据说话

2

定位瓶颈

3

对症下药

用右边这张"症状 → 处方"表选手段，一次只改一件事

4

复测归因

没变快 = 打错了瓶颈（本课程的 v2 就是活教材），回到第 2 步

REPRODUCE

在你自己的机器上复现

整个项目零依赖（gcc + make 即可），克隆后三条命令。

git clone https://github.com/…/AI-operator.git
cd AI-operator

make run            # 跑基准：256 / 512 / 1024，输出 GFLOP/s 与加速比
make run ARGS=2048  # 大矩阵：见证 v0 的 47 秒与 v5 的 0.07 秒
make check          # 用 61/260/517 等尺寸验证边角处理的正确性
make o3             # 对照组：-O3 自动向量化能白拿多少
make cblas          # 对照组：OpenBLAS 天花板（需 libopenblas-dev）
